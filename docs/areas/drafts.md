## What it does

Every unsent message for an item waits in one store, `Drafts` (`drafts/<slug>.json`), until the user sends it from the GUI: diff comments and GitHub review drafts ([review](review.md)), page annotations from a dev server's page overlay, and comments on issue drafts. Only **Send to chat** turns chat drafts into one pasted message; review drafts go to GitHub instead.

**Kinds.** `diff-comment` and `github-comment` (`LINE_KINDS`: `path`, `side`, `line`, `code`, `range`, `start_line`, `start_side`, `branch`, `committed`, plus `PR_FIELDS` for GitHub ones); `thread-reply` (`REPLY_FIELDS`); `review-summary` (`ReviewSummaryDrafts`: `repo`, `number`, optional `verdict` — `approve`|`comment`|`request-changes` — and `author`; the comment is the summary body; one per PR, a put replaces it whole and a blank one removes it; `review_summary(repo, number)` finds it and `forget_review_summary(repo, number, rev:)` removes it, only at that rev when given — what a submitted review does; `qm draft add --summary` writes it, [review](review.md)); `issue-comment` (`file`, `block`, `title`); `annotation` (`page`, `selector`, `text`, `html`, `component`, `components`, `owners`, `context`, `regions`, plus the batch's `url`/`title`; owners keep only `name`, `as`, `file`, `line`, `via`, `code`; other keys dropped). Every entry has a stable `id`, `comment`, `rev` (bumped on each edit of the comment), `createdAt`/`updatedAt`. `CHAT_KINDS` = `diff-comment`, `annotation`, `issue-comment`.

**Actions.** `draft-put` (a line draft → `{draft}`), `issue-comment-put` (`{file, block, title, comment}`), `draft-edit` (`{id, comment}`, text only, never blank), `draft-delete` (`{id}`), `drafts-discard` (all, or `{ids}`), `drafts-send` (`{branch, base, ids?}`). Send pastes one message: `DiffComments.message` for the diff comments in path:line order, then one `PageAnnotations.message` section for all annotations (a blank `page` filled from its batch's `url`; the newest annotation's `url`/`title` stand for the page sent from), then `IssueComments.message` ([issues](issues.md)) — via `paste_into_chat` — then removes exactly the entries it snapshotted (`Drafts#remove` by id and rev).

**Page annotations.** qm takes annotations from any dev server whose pages carry an annotation overlay implementing this contract (none is bundled): the user picks elements on a served page, comments on each, and sends the overlay's tray. The overlay hands them to its dev server, which relays them server-side to `POST /api/action` on `QM_GUI_PORT` (default 49737) without `Origin` (a `LoopbackGuard::LOCAL_ACTIONS` entry). Contract: `{cmd: "page-annotations", args: {root, url, title, annotations: [{comment, page, selector, text, html, component, components, owners, context, regions}]}}` → `{ok: true, slug}` or `{ok: false, error}`; `root` is the absolute checkout the dev server serves. `GuiActions#gui_page_annotations` stores them as drafts of the item found from `root` (`GuiState#items_checked_out_at`, the mapping `served?` uses: its branches checked out in its project's repo, by realpath; of several, the first in `ChatAttention` order — live chats by turn state, then most recently active). No chat needs to be open.
- Fields: `component` is the element's React component (via its fiber); `components` the chain outward, innermost first (≤ 6, wrappers and internals skipped); `context` one string of landmarks (nearest heading or card/modal title, ancestors with id, `aria-label`, `data-testid` or role) to tell identical elements apart; `regions` the landmark regions open at capture (`sidebar "Review" open · …`); `owners` `[{name, file, line, via?, as?, code?}]`, the components that *rendered* the element (React's dev-only `_debugOwner`, `node_modules` skipped), `file`/`line` where the JSX producing it is written (source-mapped by the overlay, left out when unmappable).
- What qm expects of the relayed owners: the overlay walks the whole owner chain (up to ~30, skip-list filtered); the relay resolves name-only owners by their component's unique definition under `app/javascript`, or the one candidate sharing a directory with the nearest filed neighbour (`via: "definition"`), moves one onto its JSX line when the page's `renders` tag occurs exactly once in the definition (dropping `via`), sets `as` for an aliased, default or `lazy()` import, and relays the innermost 6 owners with an app file (topped up with name-only ones when fewer than 2).
- `PageAnnotations.message`: a header naming the page most annotations share (an annotation's own `page`, else the batch `url`; first of a tie). When that is the batch's `url` it carries title and URL; otherwise the URL alone plus ` (sent from <path+query>)`. Per element: the comment, `page:` only when not the header's, `selector:`, then `rendered by:` (one line per owner, innermost first: `Name · JSX in path:42`, `Name · defined in path:12` for `via: "definition"`, `Name` alone without source, `Name (as <Alias>)`; any other `via` reads as "JSX in"), else `components: A < B < C`, else `component:`; then `context:`, `regions:`, `text:`, `html:`, each squeezed to one line.

**Clipboard load.** Where the overlay can't relay (e.g. a page reached through a public tunnel, where it should stay read-only), its tray's **copy** puts a readable message on the clipboard followed, last, by a fenced ```` ```pf-annotations ```` block holding one JSON line `{"v":1,"id","url","title","annotations":[…]}` (entries as the relay would send them, no `code`). The chat toolbar's **📋 load** (`loadClipboardAnnotations`) reads `navigator.clipboard.readText()` and posts `drafts-load` `{text}` (an ordinary page POST with our Origin). `ClipboardAnnotations.parse` takes only the last block and checks `v` = 1, an `id`, 1–100 entries, ≤ 512 KB. `ClipboardAnnotations.quote` gives each owner with a `file` and positive `line` the `code` the relay would have sent, read from the item's chat checkout (`BranchDiff#chat_checkout`: the live pane's directory, else `Launcher#start_cwd`, to its git toplevel). The entries go in through `Drafts#add_annotations` with `load_id`. The page toasts "N annotations loaded", marks the ids seen and leaves the diff closed.

**Anchoring** (`annotationAnchor(draft, diff)` in `gui/js/anchors.js`, pure, no DOM — runnable under node alone). In the whole-diff view, owners innermost first, counting only those whose `file` is in the diff: the first whose `line` is a shown branch-side line (added or context) decides — when its `code` equals that line's text, trimmed, the annotation gets a **row** under the line (`tr.d-annot`, after a diff-comment row); without `code` or with other text, a **badge**. Otherwise the innermost owner with a file in the diff badges that file's header ("N annotations"); none → tray only. Rows are violet with page icon, page path, comment, ✎/✕ and folded details, edited in place (`draft-edit`; saved empty deletes; a rebuild keeps an open editor's text) and still sent as annotations. A badge click opens the tray and flashes its first entry.

**The tray** (`gui/js/drafts.js`, one `#diff-tray` moved under whichever of the diff or Issues pane is open, `renderDiffTray`). Collapsed to "N to send · x comments · y annotations" with **Send to chat** (`drafts-send` with the ids the tray showed and the diff's branch/base) and **Discard** (confirms, then `drafts-discard` with those ids). GitHub drafts come first, one group per PR (`GitHub · widgets#7 — N review comments`, **Post as pending review**, its own Discard), then "For the chat": diff comments in path:line order (click `path:line` to scroll there), annotations as they arrived (page icon, innermost owner's `file:line`, page path, comment, details folded; anchored ones one line that scrolls to and flashes their row or badge), issue comments under "On the issue drafts" (issue title and block's first line, "the whole issue" for a title comment; a click opens the Issues pane at it). Every entry has ✎ (or click the comment) and ✕. Annotations wear violet (`--annot*` tokens), diff comments the accent, review drafts `--good`. **The chip** "N drafts" beside the header's Diff button opens the tray expanded (violet with annotations; issue comments count as comments; the Issues pane when they are all that waits). **Arrivals**: a toast, never a view switch or macOS notification — from a state, annotation ids not seen before; off the chat view, `/api/attention`'s `draftCounts` rising.

**Issue drafts.** The `/draft-issues` skill writes one markdown file per GitHub issue to `issues/<slug>/NN-short-name.md`, the directory `qm issues-dir SLUG` prints (creating it; the slug must name an existing item; only the skill mentions it). Frontmatter: `title` (required), `kind` (`feature`|`bug`, required), `group`, `parent`, `deps` (a list; a lone string is one dep; `—`/`-`/`none`/blank mean none), `change` (the latest revision's one sentence), `number` (once created; an integer or `"#40"`); then the body. Unknown keys ignored. `IssueDrafts#read` → `{issues, errors}`: every `*.md` in filename order, uncreated first; each issue `file, title, kind, group, parent, deps, change, number, created, body` (leading blank lines and trailing whitespace trimmed), `version` (12 hex of the SHA1) and `previous`; a file that doesn't parse is `{file, error}` with a readable message. `#summary` gives each `/api/state` item `issues`: nil, or `{count, open, errors, versions}`.
- *Revisions*: `.prev/<file>.json` (`{v: 1, seen, seen_at, previous}`). A read of changed content moves `seen` to `previous` and records the new one — unless `seen` is younger than `SETTLE` (120 s), when only `seen` is replaced, so a burst of Edits is one revision. `previous` is `{title, body}` or nil. **Mark seen** (`issue-acknowledge`, `#acknowledge`) sets `previous` to `seen` and `acked: true`: reads then report `previous: nil`, `acknowledged: true`; the next new version drops `acked`.
- *Deleting*: `#delete(file)` removes the file, its snapshot and its issue-comment drafts (`Drafts#forget_issue`), and the directory once no `*.md` is left (unless something else is in it); `#delete_created` does that for every issue with a `number`. `#unsent_comments` (file → count) is what cleanup's warning names.
- *Comments*: an `issue-comment` draft's `file` is the issue file's name (no path), `block` the rendered block's trimmed source text (`""` for the whole issue), `title` the issue's (a replacing put refreshes it). The pane, `IssueComments.message` and creating on GitHub are on [issues](issues.md).

## Rules

- One store per item holds every kind; writes are read-modify-write under a mutex and a per-item `flock`, then temp file + rename, so a CLI write can't interleave with a GUI action.
- The slug must look like one (`SLUG`): no path tricks.
- One line draft per address `(range, side, line, path, number)`, one issue comment per `(file, block)` and one review summary per PR `(repo, number)`: a put on the same address replaces the text, a blank one removes it.
- A review summary is neither pasted (`CHAT_KINDS`) nor posted into the pending review (`PendingReview::POSTED_KINDS`).
- `drafts-send` is refused unless the item's chat is open in the GUI, and mid-turn (`refuse_mid_turn`); it sends only `CHAT_KINDS`, never a GitHub draft or thread reply.
- Send removes by id and rev, so a draft added or edited during the paste stays. No undo.
- The store keeps arrival order; diff comments are sent and listed in path:line order.
- The page learns of changes through `Drafts.signature` (digest of the drafts files' names, sizes, mtimes; `"0"` with none) in both `/api/pulse` values; every `/api/state` item carries its `drafts`, `/api/attention` carries `draftCounts`.
- Page annotations never reach a chat from the relay: they become drafts, and only the user's Send pastes them. A page script (stored XSS, a public tunnel) can at most add drafts that the user sees first.
- qm adds no CORS for the relay. No item on that checkout is an error saying so; empty annotations (none with a comment) are refused; an overlay should keep its tray on any `ok: false`.
- Annotation input comes from a browser: wrong types (non-array `components`/`owners`, non-string chain entries, an owner without a string `name`, a non-positive-integer `line`) are ignored.
- Message caps: page, context and the joined chain 300; each chain or owner name 80; an owner's file, regions and text 200; html 600 characters; at most 6 owners (qm caps them itself).
- `components` stays a structured array on the wire (for matching against the branch); only the message flattens it. With owners present they replace the chain in the message.
- "JSX in" names where the element's JSX is written, which can differ from the component's definition (children, render props); "defined in" marks a definition-resolved owner.
- The `pf-annotations` block is the contract between an overlay and qm; `parse` takes only the **last** block, so text quoting an older copy above it is harmless.
- Clipboard refusals are messages the page toasts: no block, bad JSON, unknown `v`, no entries; an unknown slug is `WorkItem.find`'s.
- A `code` on the clipboard is always dropped; `quote` reads it under the relay's rules: path under `app/javascript/`, no `..`, no NUL, a regular file (lstat — a symlink is refused) ≤ 512 KB, the line without CR, invalid UTF-8 scrubbed, none over 500 characters. No checkout or a refused file means no `code` (badge or tray when anchoring).
- Each drafts file keeps the newest 50 loaded ids (`loaded`); an id already there is refused ("already loaded"), also after its drafts were sent — so such a file outlives its last draft; otherwise an item left without drafts loses its file.
- 📋 load marks its own ids seen first, so no second "arrived" toast.
- Annotation anchoring: line numbers alone drift as the branch moves on; the matching `code` text says it is still the same line.
- A removed line's base number never matches an owner line; lines past the diff's truncation aren't shown; under a selected run (`diff.range`) nothing anchors — those numbers are the run's.
- Paths compare repo-relative on both sides; `repoRelative` only drops a stray leading `./` or `/`.
- The body's rebuild signature (`diffDraftsShown`) covers annotations, so an arrival or edit moves anchors at once; long files build rows on first open (`box.fillRows`), which a jump calls directly.
- Tray changes show at once (`patchLocalDrafts`) and the action's state refresh confirms them; a failed action refetches.
- The tray re-renders on every chat render, so Send follows the turn (disabled with the reason as tooltip while the chat has no GUI pane or is `working`/`blocked`); an open tray editor keeps text, caret and focus.
- Annotations are violet, never orange, which means "your turn".
- Issue comments and diff comments are the user's own: no per-id arrival toast; the count-based toast off the chat view covers them.
- Off the chat view a rising `draftCounts` slug is re-baselined by the next state, not toasted again.
- Diff comments once lived in `localStorage` (`qm-diff-comments:<slug>`); `importLegacyDiffDrafts` moves any into the store on load (`draft-put` per comment, keyed by line so a second tab changes nothing; a key goes once all its comments made it, one for an unknown item stays).
- **qm only reads issue drafts**; Claude writes them with Edit/Write. qm writes only the `.prev` snapshots and deletes files.
- Only files that parse are recorded as revisions, so a half-written save never becomes a previous version; a snapshot whose file is gone is dropped, so a recreated file starts fresh.
- Revisions and acks live on disk: a GUI restart neither loses nor invents a previous version, and an Edit still settling after Mark seen compares against the acknowledged content.
- A bad issue file (no frontmatter, bad YAML — only plain scalars load, so dates fail — missing title, unknown kind, non-list `deps`, a non-number `number`) is an `errors` entry, never an exception.
- `IssueDrafts.signature` (every `issues/*/*.md` path, size, mtime; `"0"` with none) is part of both `/api/pulse` values and that response's `issues` field; it leaves `.prev` out, so qm's own snapshot writes never move it.

## Data

- `drafts/<slug>.json`: `{v: 1, entries: [...], loaded: [ids]}`.
- `issues/<slug>/NN-name.md` (Claude's) and `issues/<slug>/.prev/<file>.json` (qm's revision snapshots).

## Known limits

- "Previous" is the last version a running GUI saw: reads happen on state builds and `GET /api/issues`.
- Not built: ⌘V paste import of annotations, and a global key finding the item by checkout as the relay does.
- An owner without stack info (React's owner-stack limit in large renders) is kept by name only; the limit depends on how much the page rendered.
- No screenshots, computed styles or element bounds in annotations.
