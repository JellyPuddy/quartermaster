# Issues

**Code:** `lib/quartermaster/issue_start.rb`, `lib/quartermaster/issue_links.rb`, `lib/quartermaster/gui_issue_actions.rb`, `lib/quartermaster/issue_index.rb`, `lib/quartermaster/issue_comments.rb`, `lib/quartermaster/gui/js/issue-start.js`, `lib/quartermaster/gui/js/issues.js`, `lib/quartermaster/gui/js/issues-list.js`, `lib/quartermaster/gui/css/issue-start.css`, `lib/quartermaster/gui/css/issues.css`, `lib/quartermaster/gui/css/issues-list.css`
**Tests:** `test/issue_start_test.rb`, `test/issue_links_test.rb` (real issue bodies, names changed, in `test/fixtures/issue-bodies/`), `test/epic_sub_issues_test.rb`, `test/issue_comments_test.rb`, `test/issue_cleanup_test.rb`
**Depends on:** [drafts](drafts.md), [worktrees](worktrees.md), [linking](linking.md)

## What it does

Three things: starting a work item from any GitHub issue, the Issues pane beside a chat (an item's issue drafts, with comments), and the cross-item Issues view. The issue-draft files themselves, their parsing, revision snapshots and `IssueDrafts.signature` are in [drafts](drafts.md).

### Start from an issue (`IssueStart`)

- **Repo**: the project's root (`ProjectMap#root_for`) and its `origin` remote's `owner/name`; no root or no GitHub remote → refused.
- **Preview** (read-only): one `gh api graphql` call through `CommandRunner` (`IssueStart::QUERY`: number, title, state, url, body, `issueType`, the first 100 `subIssues` and comments) → number, title, state (`closed` still startable, flagged), url, project, repo, the branch it would create or reuse (`reuse_branch`), the item slug, or the item already holding it (`existing`, with its `epic` flag), plus `epic`, `links` and `sub_issues` (`{number, title, state, url}`, GitHub's child issues). An unknown number is an error. `#1234` and `1234` both parse.
- **Epic issues**: an issue is an epic when its `issueType` name is in the project's `epics.issue_types` (case-insensitive; unset → never).
- **Links** (`IssueLinks`, the one place links are derived from an issue): every item started from an issue carries them — normal, inside an epic, or an epic — and `IssueStart#refresh_links(item)` reads them fresh for any item whose description has a GitHub issue URL (↻ links, `qm link SLUG --refresh`, [work-items](work-items.md)). From the project's `issue_links.*` settings, in this order: **Tracker** — `tracker_url` with `{repo}` (owner/name), `{owner}`, `{name}`, `{number}` filled in; the Notion link, labelled `notion_label` (default `Notion`) — the first notion.so/notion.com URL in a comment whose author login is `notion_author`; then one link per `heading_links` rule (`Design`, or `Heading=Label`), in rule order: the first markdown heading (`#`…`######`) whose text contains the word (any case), and the first http(s) URL in its section, up to the next heading, stopped at whitespace, `)`, `]`, `<` or `>`. HTML comments (`<!-- … -->`) are removed first, headings and URLs inside them included; only the first matching heading counts. A missing setting, comment, heading or URL skips its link; a label or URL already taken by an earlier link is skipped.
- **Duplicates** (`existing_item`): an item of the project with an `issue/<n>` or `issue/<n>-*` branch linked, or any item whose description carries the issue URL (not a longer number's). Unresolved first, then the branch holder. An issue of another repo than the project's (a sub-issue elsewhere) is found by its URL only.
- **Sub-issues**: starting an epic attaches every item already holding one of the preview's `sub_issues` (`existing_item`) to it with `join_epic`, except an epic, an automation or an item already in another epic, which stay put; the start returns `attached` (slugs) and `skipped` (`{slug, reason}`). `IssueStart#sub_issues(epic slug)` reads them fresh from the GitHub issue the epic's description links (none linked → `[]`; not an epic → refused): `{number, title, state, closed, url, item, startable}`, `item` the holder's slug or nil, `startable` only for an issue in the project's own repo.
- **Start**: branch `issue/<n>-<title slug, ≤40 chars cut at a word boundary>` from `origin/<default>` after `git fetch origin <default>` (default = `origin/HEAD`, else `gh repo view`), `--no-track`. A local `issue/<n>-*` branch no item links is reused instead, without a fetch. The worktree is made through `TargetWorktree#materialize_branch` (with `<test_db> prepare` where configured) **before** the item. Item: title `<issue title> (#<n>)`, slug from it, description = URL + title only, in_progress, the branch linked, the preview's links in `links:`. `from:` (a drafting item) gets a `history` note `#<n> started as <slug>`. `as_epic:` (default: the preview's `epic`) makes a `kind: epic` item instead — same title, slug and description, the preview's links in `links:`, no branch, worktree or fetch (`target` nil). `epic:` puts the new item inside that epic (`epic:` front key at creation), checked before any worktree; an epic issue started inside an epic defaults to a normal item.
- **Kickoff**: a fresh `QM_ITEM` chat (`Launcher#chat_plan(…, prompt:)`) with the kickoff as claude's argument, not typed: "Read issue #<n> (`gh issue view <n> --comments`), summarise the problem, then run a grilling session (the grilling skill) with me on how to solve it. Don't change code yet."
- **GUI actions** (`GuiIssueActions`): `issue-preview` (`{number, project}` → `{ok, issue}`; off the action mutex, `GuiActions::UNLOCKED`) `epic-sub-issues` (`{epic}` → `{ok, sub_issues}`, `IssueStart#sub_issues`; also unlocked) and `issue-start` (`{number, project, from?, as_epic?, epic?}`, `epic` refused up front unless it may hold the new item; project defaults to config.yml's `default_project`, else its first project). An existing holder → a resolved one back to in_progress, then an epic answers `{ok, existing: true, epic: true, slug, issue}` and opens nothing; any other resumes its chat via `gui_pane`, `{ok, existing: true, slug, mode|attached, issue}`. `as_epic` (default the preview's `epic`) → the epic is made at once, no job, no chat: `{ok, slug, epic: true, issue, attached, skipped, message}`, the message naming what joined and what was left out (and why). Otherwise a `GuiJobs` background job keyed by the new slug answers `{ok, background: true, slug, issue}` at once, relabels per step ("fetching origin/main…", "creating the worktree…"), opens the chat in the item's tmux session and finishes with `{ok, slug, branch, path, message}`.
- **CLI** `qm start-issue N [--project P] [--as-item] [--epic SLUG]` (default: the cwd's project, else config.yml's default project) prints the preview and its links (an epic issue adds a ◆ line, unless `--epic`, which adds "inside epic SLUG"), then POSTs `issue-start` to the running GUI (a `LoopbackGuard::LOCAL_ACTIONS` entry; `--as-item` sends `as_epic: false`, `--epic` sends `epic`). An epic start prints `joined:` and `left out:` lines. No GUI → an existing holder is named (`qm resume <slug>`; an epic holder only by name, and the preview's ◆ line is left out), an epic issue becomes the epic item, else it creates item + worktree itself and prints the `cd … && QM_ITEM=… claude '<kickoff>'` line.

**The page side** (`issue-start.js`): every entry point ends in one confirmation modal (`issueStartModal(number, project, {from, epic})`; `epic` rides on the preview as `into`, shown as an Epic fact and sent as `issue-start`'s `epic`). It fetches `issue-preview` straight from `/api/action` (no state refresh; a failure shows in the modal, not as a toast) and shows the title (linked), state (closed: a warning, Start still offered), project and branch (new off origin's default, or "reuses this local branch"). An existing holder replaces the branch line and Start reads "Open its chat" ("Open the epic" for an epic holder). An epic issue (the preview's `epic`) carries a ◆ Epic badge (epics.js's `.epic-kind`) and, unless held already, a **Start as epic** switch, on by default: on, the branch line becomes the would-be links as `linkChips` draws them and Start reads "Start as epic"; off, the modal and Start are the normal ones. Start sends the switch as `as_epic` (false for an issue that isn't an epic). A start inside an epic (`into`) shows neither badge nor switch and sends `epic` instead of `as_epic`, so the server makes a normal item in that epic.

- **Entry points**: (a) the ＋ New item modal's "From issue" row — `123`, `#123` or `project#123`, its own project picker (the context project, else the state's `defaultProject`; never "No project"), Look up / Enter; (b) the search box when the whole text is `#1234` or `project#1234` (project matched case-insensitively): the search menu offers "Start work on #1234 (Project)" and ⏎ takes it instead of Ask (Ask stays clickable). A bare `#n` means the shown chat's project, else the detail sheet's item, else the focused card's, else the server's default project (the state's `defaultProject`). As a board filter `project#1234` is `#1234` narrowed to that project; (c) a created draft (frontmatter `number:`) — Start work in the Issues pane beside Copy markdown, and in the Issues view (row button, `s` on the focused row), passing the drafting item as `from`.
- **An epic's sub-issues** (`chatEpicSubIssues` in `chat-epic.js`, the side panel's Epic block): for an epic whose description links a GitHub issue, `epic-sub-issues` is fetched straight from `/api/action` the first time the block shows it and on the label's ↻, cached per epic slug (`epicSubIssues`) because the panel re-renders every poll. It lists the sub-issues no item holds (no `item`, and no item's description carrying the URL), each linked to GitHub, closed ones dimmed (still startable, like any closed issue), each startable one with a Start → `issueStartModal(number, epic's project, {epic})`. Once that start is taken the row reads "starting…" (`epicSubIssueStarted`) until the new item hides it.
- **What a draft became** (`issueBecame`): instead of Start work, a created draft's row links `→ slug` to the item it became — the drafting item's `#<n> started as <slug>` note, else any item holding the issue by the duplicate rule (unresolved first). The drafting item itself never counts.
- **Start**: an existing holder → its chat opens (`openItemChat`) with the toast "#n is already <slug>: opened its chat". An epic answer (`epic: true`, made now or held already) closes the modal, toasts and opens the epic: `openItemChat` lands an epic on the chats view with its Epic block, the terminal unfocused and no chat started, as it does for a draft's `→ slug` link to an epic. Otherwise the modal shows a spinner with the job's current label and a Hide button (the job carries on). The tab remembers the job keys it started (`issueStarting`); `jobFinished` hands every finish to `issueStartFinished`, which closes the progress modal and opens the new item's chat on success. A failure is jobFinished's usual error toast.

### The Issues pane (`issues.js`)

- An **Issues · N** button sits beside Diff in the chat toolbar while the item's state carries `issues` (any file, broken ones included). The pane `#issues-pane` is a second `.diff-pane` in the diff's slot: opening one closes the other (`setIssuesOpen`/`toggleDiff`). Open/closed is remembered per chat with the diff's (`qm-side-panes`); the side panel steps aside (`body.issues-open`) and the maximized terminal hides it.
- It fetches `GET /api/issues/<slug>` (`{ok, slug, repo, issues, errors}`, off the action mutex; `repo` = `Owner/Name` of the project checkout's `origin` via `Quartermaster.github_repo`, nil when unknown) when it opens and whenever the item's state summary changes (its JSON is the reload key) — never on every state.
- **Left, the group nav**: open drafts under their `group` (first-seen order, headed only when there are several sections), then **Created on GitHub**, then **Unreadable** (file + parse error). Tabs numbered, with kind and a dot when `change` is set; a created one shows `#n`.
- **Right, the issue**: title, **Copy markdown** (the body), kind pill, GitHub link `Owner/Name#n` (plain `#n` without a repo), `Parent: #…`, `Depends on:`, the `change` sentence, a legend when blocks are marked, then the body rendered by `marked@12.0.2` (pinned jsdelivr tag with SRI). Without `marked` (offline CDN) the body is plain text, unmarked.
- **Changed blocks** are marked client-side against the server's `previous` body, with the same splitter that anchors comments (`issueBlockSources`/`renderIssueBody`): `marked`'s lexer, each top-level token's `raw`, but per item for lists and per line for tables (delimiter row skipped); `space` and link-definition tokens are no block. A current block whose trimmed source text isn't among the previous body's blocks is new or reworded. A created issue gets no marking. **Mark seen** (legend or change banner, `issue-acknowledge`) clears the marking, the `change` banner and the tab's dot, persistently.
- **Created issues** are read-only: a note says so, no new comments, no create button. **Clear created** in the bar (shown while any exists, after a confirm) runs `issues-clear-created` (`IssueDrafts#delete_created`, `{ok, cleared: [file]}`).
- **Revision toasts**: every state's `versions` are compared with the last state's; a file whose version moved is revised. The toast ("2 issues revised", plus "for <slug>" when that item's chat isn't shown) waits until the item's files were still for 4 s, counting each file once. Never a view switch or macOS notification; arrivals show only as the button's count. Off the chat view, a revision is toasted with the next action's state.
- **Without a live chat**: the detail sheet shows an **Issues (N)** row (to create · created · unreadable) that opens the item's chat view with the pane, terminal unfocused (`openIssuesFor`). No new keyboard shortcut: the pane's tabs are buttons.
- **Commenting**: every block element — heading, `p`, `pre`, `blockquote`, each `li` (nested lists stay inside their item), each table `tr` — has class `iss-block` and `data-src` (its trimmed source text); raw-HTML blocks are wrapped in a `div` carrying the same. A click on a block, or on the title (`.iss-title[data-issue-target]`, the whole issue), opens a comment editor (⌘⏎ saves, Esc cancels; a click ending a text selection doesn't open one). Saving puts an `issue-comment` draft (`issue-comment-put`: file, block source, title); a blank one removes it. Comments render from the drafts on every rebuild, matched by **exact** source text: a row after the first block with that text (inside a list item; under a table row as a full-width row), whole-issue ones under the meta line, and those whose text no block has any more at the issue's top, "on a block that changed", quoting the old text (amber). The pane rebuilds when the item's issue comments move (`issueDraftsShown`, from `draftsChanged`); an open editor comes back with its text, focus and caret when its block is still shown.
- **Create on GitHub** — in the issue's header for one issue, "Create all N on GitHub" in the bar while more than one is uncreated — runs `issues-create` (`{files?}`): qm pastes into the chat a request to create the given drafts (all uncreated when `files` is absent) "per the /draft-issues skill's create step", naming the issues directory and each file with its title, and asking for `number:` in each created file's frontmatter → `{ok, requested: [files]}`. It and the tray's Send are disabled with Send's reason (`diffSendBlocker`: no chat open in the GUI, or working/blocked), re-checked on every chat render.
- **The tray** under the pane is the drafts tray itself: the one `#diff-tray` element moves to whichever pane holds the slot (`renderDiffTray`). Issue comments follow the diff comments and annotations under "On the issue drafts", each with its issue's title and the block's first line ("the whole issue" for a title comment); a click opens the pane at that issue and flashes the comment (`revealIssueComment`). The summary and the chat header's chip count them ("1 issue comment"); the chip opens the tray under the open pane, or the Issues pane when issue comments are all that waits. Like diff comments they raise no per-id arrival toast.

**Sending issue comments** (`IssueComments.message`, the last section of `drafts-send`): a header naming the issues directory, then per file in filename order a `## <file> — <title>` heading and its comments — whole-issue ones first ("On the whole issue:"), then each block's source quoted with `> ` before the comment, in body order. The body is read at send time; a block no longer contained in it sends after the others, still quoting the text it was made on, with a line saying it changed since. A file gone from the directory keeps its comments' stored title and its heading says it is no longer in the drafts; a file there that doesn't parse says it doesn't parse right now.

### The Issues view (`issues-list.js`)

- The fourth header mode `Issues` (`data-mode="issues"`, key **⇧I** — `e.key === "I"`; plain `i` stays the chat view's detail), remembered in `qm-mode`. Its badge is the sum of `items[].issues.open` from `/api/state` (drafts not yet on GitHub; hidden at 0), redrawn every render.
- When `/api/pulse`'s `issues` field moves, the page refetches the state in every mode, so the badge doesn't go stale off the chat view; the view refetches `GET /api/issues` when it opens and on that move while shown.
- `GET /api/issues` (off the action mutex) is `{ok, items}` from `IssueIndex#entries`: one entry per work item whose `issues/<slug>/` holds a `*.md` — `{slug, title, state, repo, changed_at, issues, errors}`, `repo` resolved once per project, `changed_at` the newest `*.md` mtime (UTC ISO 8601), `issues` only `{file, title, kind, number, created}` (no bodies). Order: in_progress, fridge, resolved, then newest `changed_at` first. It reads through `IssueDrafts#read`, so it records revision snapshots like the pane.
- One group per entry: state chip, the item's title and slug, its tally (to create · created · unreadable). Rows: the file's leading number, title, kind pill; a created issue dimmed with `#n` (linked to `github.com/<repo>/issues/n` when the entry has a repo); a broken file a `⚠ file` row with its parse error.
- j/k/arrows move the focus (kept by `<slug>/<file>` across refetches); ⏎ or a click opens the row: `openIssuesFor(it, file)` — the item's chat view with the pane on that file's tab (`issuesPick`; a broken row passes no file). An item missing from the last state is fetched first.

## Rules

- qm only **reads** GitHub for issues: nothing is assigned, labelled, moved or commented, and issue creation is asked of the chat — qm never runs `gh issue create`.
- No tracker or bot name lives in code: epic issue types (`epics.*`), the Tracker template, the Notion comment's author and label and the heading rules (`issue_links.*`) are per-project settings.
- Links come from the one `gh api graphql` read a preview or refresh already makes; never an extra gh call, and qm never reads Notion.
- An epic started from an issue never gets a branch, worktree, chat or kickoff, then or when started again.
- The issue branch is `--no-track`, so its upstream is never main; it becomes its own once pushed.
- The worktree is made before the item, so a retry after a failed item step finds the branch unlinked and reuses it.
- The item's description is URL + title only, never the issue body: the description is re-injected every session.
- The kickoff is claude's argument, never typed into a pane.
- `issue-preview` and `epic-sub-issues` run off the action mutex: they wait on GitHub and change nothing. Sub-issues are read only on demand (the Epic block opening, its ↻), never from the state build or a poll.
- An epic start moves no item out of another epic, and never makes an epic or automation a child.
- `qm start-issue` asks no y/N: chats run it too, and the preview is there to read afterwards.
- The page marks the job key from the preview's slug *before* posting `issue-start`, since the action's own state refresh can already carry the finish.
- An issue body must never run script (the page runs actions on the loopback port): raw HTML renders as text and links other than http(s)/mailto/`#` lose their `href`.
- Comments match blocks by exact source text and are never re-anchored: a comment whose block changed shows as stale, quoting its old text. The server's stale test is plain containment of the trimmed text in the body; the pane's splitter decides what shows as stale.
- `issues-create` is refused like `drafts-send` (no chat open in the GUI, mid-turn), for an empty choice, and for a file that is missing, broken or already created.
- Revision toasts never switch views and never raise macOS notifications.
- The Issues view is read-only by design: creating, deleting and commenting stay in the pane.

## Data

- `issues/<slug>/*.md` and `.prev/` — owned by [drafts](drafts.md).
- `issue-comment` entries in `drafts/<slug>.json`: `file` (the issue file's bare name), `block` (trimmed source text; `""` = the whole issue), `title`, `comment`. One draft per (file, block).
- `/api/state` per item: `issues` = nil without files, else `{count, open, errors, versions}` (`file → version` for parsed files).
