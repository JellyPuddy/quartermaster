## What it does

Comments made on diff lines become drafts ([drafts](drafts.md)): chat drafts, pasted into the item's chat as one message, or — in the PR scope — GitHub drafts, posted into the user's pending review on the PR. The PR's review threads show in the diff, with reply and resolve.

**Diff comments.** Clicking a diff line opens an editor under it (⌘⏎ saves, Esc cancels; a click that ends a text selection doesn't). A line is addressed by path + side + number: a removed line by its base number (`side: "old"`), anything else by its branch number. A comment made under a selected run of commits carries the run's `range`, shows only under that selection, and its message says `(on commit abc1234)` / `(on commits abc1234..def5678)`. It also stores the `branch` the pane showed, and `committed: true` when that branch had no checkout. Clicking a tray entry written elsewhere switches the pane to its view — its branch when the picker offers it (Branch scope for a ref-only one), the PR scope for a PR draft, its commit selection — and shows it (`showDraftView`, `diffDraftBranch`).

`DiffComments.message` is the chat section: a header naming branch and base, then per comment `path:line` (+ "(removed line)"), the line quoted with `> `, the comment. The header names the comments' branch when they all agree (a comment without one takes the pane's branch at send time), the base only when it is the pane's branch; when they differ each comment says "on branch X". A `committed` comment outside Commits/PR says "as committed, not on disk". Ranges read `path:12-15` (`old 12-new 15` across sides) and quote each line; a PR-scope chat draft reads `path:line on widgets#7 @abc1234` (`pr_label`).

**The line editor.** In the PR scope it saves **Add to review** (⌘⏎, primary, green — review drafts wear `--good`, chat drafts the accent) or **Ask chat** (⌥⏎); elsewhere **Save** (⌘⏎ or ⌥⏎) makes a chat draft. Add to review on a `gh: false` line replaces the buttons with "GitHub can't take a comment on this line at <sha7>…" and **Save as file comment** (⌘⏎, `subject: "file"`) / **Ask chat** / Cancel. **Suggest change** (every scope, only when both ends are added/context lines) inserts a ```` ```suggestion ```` block with the lines' text at the caret. **Ranges**: a click remembers a line; ⇧-click on another line of the same hunk opens the editor under the later line for the span (`diffRangeAddress`, rows `d-range-sel`); clicking a saved range draft's last line edits it (`diffEditAddress`); built files mark saved ranges (`markDiffDraftRanges`, `d-in-range`). A saved PR-scope draft shows a tag — `review`/`chat`, 🤖, file comment, lines — with the move chip (`→ chat` / `→ review`, `draft-move`).

**GitHub drafts.** Kind `github-comment`, a line draft like `diff-comment` (`Drafts::LINE_KINDS`) with `PR_FIELDS`: `repo`, `number`, `base` (the PR's base sha), `commit` (the anchor: the head at draft time or the selected run's last commit — `diff.anchor`), `subject` (`line`|`file`), `author` (`user`|`claude`). A chat draft made in the PR scope keeps `repo`/`number`/`base`/`commit`. Line drafts may carry `start_line`/`start_side` (the address stays the range's last line, where GitHub shows it), `code` joining every line's text. `Drafts#move(id, "github"|"chat")` is the chip. `DiffComments.github_body` is the posted body: the comment as written (a suggestion block is GitHub's), a file comment's lines quoted above it (`Line 4:` / `Lines 3-4:`).

**Review anchors** (`ReviewAnchors.new(repo, base:, commit:)`). GitHub validates a comment anchored to commit X against `merge-base(base, X)..X`, only inside its hunks (3 context lines included), and joins hunks one unchanged line apart — `--inter-hunk-context=1` (`GITHUB_HUNKS`) reproduces its hunks, so the PR scope uses it too. Per `(path, side)` (LEFT/RIGHT, or `old`/`new`) it answers `lines`, `commentable?`, `text` and `position` (the 1-based position `addPullRequestReviewComment` takes: the line under the first `@@` is 1, later `@@` headers and `\ No newline` markers count). `file(path)` is `UnifiedDiff`'s file with each line's `p`, a deleted file found by its old path. `anchorable?(path, side, line, text, view_base:)` = inside the hunks *and* still that text (`view_base`: what the view diffed from — a selected run's parent, else the PR's base). `refusal(entry, view_base:)` says why a draft won't anchor, or nil; `ReviewAnchors.refusal(repo, entry)` builds it from a stored draft (`view_base` = the parent of `range`'s first sha). In the PR scope with a run selected each line GitHub won't take carries `gh: false` (`BranchDiff#mark_unanchorable`); the whole PR's view is `base..head` and carries no marks.

**Review threads.** Once the PR scope's diff shows, the page asks `GET /api/pr-threads?repo=&number=&head=` (request thread, never the action mutex). `ReviewThreads#fetch`: one `gh api graphql` per 50 threads (≤ 10 pages) — path, line/startLine (null once GitHub can't place it), originalLine, side, subject, resolved/outdated, resolvedBy, viewerCan*, every comment — plus the viewer's pending review and the PR's node id. `quote` is the last line of the first comment's `diffHunk`, GitHub's own quote, also for outdated threads. The diff never waits on this fetch. The pane (`gui/js/pr-threads.js`) puts a thread under its line when the full PR diff (no selection) shows it on its side; the rest fold into "N threads on unchanged lines" atop the file (line number, original once outdated, quoted line); file comments sit open on top; threads on unshown files fold above the files; resolved ones fold to one line. File headers show `💬 open/all`, the bar the total. **Resolve/Unresolve** (`pr-thread-resolve`) is immediate, no confirmation, then a fresh fetch. **Reply** makes a `thread-reply` draft (one per thread, blank removes; `thread`, `repo`, `number`, `url`, display `path`/`line`, `author`).

**Claude's review drafts** (`ChatReviewDrafts`). `qm draft add SLUG --path P --line N [--start-line M] [--side old|new] [--commit SHA] [--file] [--reply-to THREAD_ID] [--pr URL] [--branch B] (--body TEXT | --body-file F|-)` records a finding as a GitHub draft with `author: "claude"` (🤖 until the user edits its text). Which PR: `--pr` (cache, else `gh pr view`), else a Review item's own, else `--branch`'s open PR, else that of the branch checked out in the cwd when the item links it, else the item's only linked branch with an open PR; several or none errors naming `--branch`/`--pr`. Line numbers are those of `base..anchor` (the PR head, or `--commit`, which stores `range` from the PR's first commit to it — its short sha alone when it is the first, none when it is the head), so the pane shows it under that selection. A Review item's kickoff asks its chat for this. `code` comes from that diff (`ReviewAnchors#text`, `#span` for a range — every row between, removed ones included, as the pane joins them; a `--file` comment off the diff reads its line from the blob). `--reply-to` stores a `thread-reply` (`--commit`/`--file`/`--start-line` don't apply; the thread id isn't checked). `qm draft list SLUG [--json]` prints id, what and where, whose (`🤖 claude`/`user`) and first line.

**Posting the pending review.** `ReviewPlan.new(repo, base_ref:, head:)` routes each GitHub draft of one PR against the head as fetched now, with local git only:
- **head** — a thread on the head (LINE with line/side/startLine/startSide, or FILE while the file is in the PR) when its lines still read the same at the same place in `base..head`; or, for a whole-PR draft (no `range`, no `pin`) whose head moved, when its last line's text appears exactly once on its side of that file's new diff (`moved: true`; a range keeps its length and must still read the same).
- **commit** — a commit draft (has `range`) or one pinned there (`pin: "commit"`) goes on its commit by `position` in `base..commit` (`addPullRequestReviewComment` with header `GraphQL-Features: pull_request_review_comment_position`; a range posts at its last line with "Lines a–b:" leading the body). A commit a force-push removed is followed to the PR commit with the same `git patch-id --stable` (`moved: true`).
- **outdated** — neither: not posted; carries `reason`, `fileGone`, `oldCommit` (whether the commit route could take it) and `context` (old line ±3, `at` on the line; the stored text when the commit is gone). A file comment whose file left the PR is outdated with no old-commit route.

`PendingReview.reanchor` writes moves back (`Drafts#relocate`, no rev bump): a moved whole-PR draft takes its new numbers, the head as `commit` and the new `base`; one whose head moved but line didn't takes the new head; a rebased commit draft its new `commit`. The PR scope runs it on every load (`BranchDiff#review_routes` → payload `reviewRoutes`, draft id → route). `PendingReview.new(root, repo:, number:, runner:)` reads the PR (id, base, head, state, the viewer's `PENDING` reviews), fetches it and plans. `preview(entries)` → `{pr, url, count, head, commit, outdated, replies, moved, pending}` (`replies`: thread replies, which need no route; `pending`: the comment count of the user's existing pending review, else nil). `post(entries, drafts)` uses the user's pending review if they have one (one started on github.com included), else `addPullRequestReview(commitOID: head)` without an event; then one call per postable draft, replies via `addPullRequestReviewThreadReply`.

Actions: `review-preview`, `review-post` (the item's `GuiJobs` job: "N added to your pending review on widgets#7 — submit it on GitHub · M outdated, not posted", `warning` for fallbacks, `ok: false` naming the first failure), `draft-place` (`{id, how}`: `line` re-addresses onto a head line — no range, no pin, checked like a put; `file` makes a file comment on the head; `commit` pins it; the rev moves). **Page** (`gui/js/review.js`): **Post as pending review** (`postPendingReview(repo, number, ids)`: preview, confirm, `review-post`) shows "Checking the pull request on GitHub…", then a confirmation listing how many go on their commit (and may fall back), moved, outdated ("won't be posted — they stay in the tray") and whether it adds to an existing pending review; the job's toast arrives via `jobFinished` (`reviewPostFinished` re-renders the tray and reloads a PR-scope diff). In the whole PR's view each outdated draft whose file is shown is a card atop its file (`renderOutdatedCards`, `--warn`): reason, context, comment, **Place on a line** (next diff-line click places it — `diffPlacing`, crosshair, Esc cancels unless a terminal has focus), **Comment on the file**, **Comment on the old commit** (only with `oldCommit`), **Delete**; its stale line draws no comment row. Otherwise (file gone, or a run selected) the card sits in its tray entry without Place on a line, and without Comment on the file when the file left the PR. Tray entries tag `outdated` and `not posted` (GitHub's reason under the comment).

## Rules

- The diff-comment paste refuses mid-turn like `gui_type_into_chat` (shared `refuse_mid_turn`) and uses `Tmux#paste` (bracketed `load-buffer`/`paste-buffer -p -d` — `send-keys -l` would submit at every newline), the `TYPE_SETTLE` pause, one Enter.
- The pane shows a draft at its path:line on any branch; only the message tells branches apart.
- A refetch or store change rebuilds the body but reopens an open editor with its typed text.
- A saved draft's row is built from its *line's* address, not the stored draft: re-editing saves what the line says now, `gh: false` offer included; a GitHub file comment re-edited saves a file comment again.
- Emptying the box and saving deletes; a save the server refuses reopens the editor with its text (it closes optimistically).
- A range across a hunk header toasts and does nothing; an open editor's range survives a rebuild, and one already open on the later line keeps its text.
- One address `(range, side, line, path, number)` holds one line draft of either kind; the PR number keeps PR-scope drafts apart from the same line in Branch/Commits. A put of the other kind reshapes it (`Drafts#reshape`; rev moves only on a change).
- `draft-put` of a `github-comment` and `draft-move` to `github` are checked first with `ReviewAnchors.refusal` in the project's main checkout (it has the fetched PR objects) and refused with the reason; move to the review needs a draft that knows its PR.
- A file comment keeps `subject: "file"` through a trip to the chat, so it comes back one.
- An edit that changes a `claude` draft's text makes it `user`'s; a put that leaves the text alone keeps the stored author, one that changes it takes the put's (default `user`).
- A range must sit inside one hunk of `base..commit` (GitHub takes a range only inside one; the view's hunks can differ under a selected run), both ends checked.
- A removed line anchors only when `view_base` is GitHub's base, since its number is `view_base`'s; a file comment needs only its file in the diff.
- `ReviewAnchors` parses its diff once per instance and indexes lines per path and side: `mark_unanchorable` asks for every shown line.
- `qm draft add` validates with the editor's check; a refused line comment errors with the reason plus "Record it as a file comment with --file instead" — never quietly converted.
- A put on an address or thread holding Claude's own draft replaces it (reported); one holding the user's draft (any chat draft, or a GitHub draft they wrote or edited) is refused, checked under the drafts lock.
- A PR outside the project's repo is refused, for the CLI as for the pane.
- The CLI writes `drafts/<slug>.json` directly, GUI running or not; no GUI action or `LOCAL_ACTIONS` entry is involved — the page learns through the pulse.
- Review drafts and thread replies are never pasted into the chat: `drafts-send` sends only `Drafts::CHAT_KINDS`.
- Thread replies sit in their PR's tray group after its comments (`isReviewDraft`) and post with them.
- `ReviewThreads` caches per `repo#n@head` for 30 s: a push is a new key; ↻ (`fresh=1`) and every write through the class skip or drop it.
- A `PENDING` comment is always the viewer's own (GitHub shows nobody else's), so it shows "pending (yours)".
- Threads sit under lines only in the full PR diff — a run's numbers aren't the PR's; a context line is both sides.
- `pr-thread-resolve` and `review-preview` are `GuiActions::UNLOCKED`: they touch only GitHub (and a fetch).
- `PendingReview` sends everything through the runner as `gh api graphql`, strings as `-f` (never read from a file), ints as `-F`; a GraphQL `errors` list or failed exit is an `ArgumentError` with GitHub's message.
- A head that moved between fetch and plan refuses the post — try again.
- Every post result is checked: a null thread/comment (GitHub's silent refusal) or an error leaves the draft with `failed: "<why>"` (`Drafts#mark_failed`; an edit, put, move or relocate clears it); a reply that comes back with no comment raises.
- A commit-route error falls back to a FILE thread on the head with body `on <sha7>, path:line:` + the quoted lines + the comment; a failure too when the file isn't in the head's diff.
- Posted drafts leave the store by `{id → rev}` (one edited while posting stays); outdated ones stay.
- qm never submits a review: the user does, on GitHub, with their verdict.
- `Drafts#relocate` doesn't bump the rev: nothing the user wrote changed. A diff load whose routes moved a draft refreshes the state so it shows on its new line.
- Placing a draft leaves Esc to a focused terminal.

## Known limits

- The `\ No newline` position counting is the patch-text reading of GitHub's rule, not yet seen on GitHub.
- The commit route relies on a flagged GraphQL feature (`pull_request_review_comment_position`); the file-thread fallback covers its loss.
- Outdated threads come back with `line: null` and `isOutdated: true`; a single-line thread may carry `startLine` equal to `line`.
